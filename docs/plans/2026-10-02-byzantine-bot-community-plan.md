# Byzantine Bot Construction Plan: Community-Derived Strategy Through the .per Compiler

Date: 2026-10-02
Status: refined working strategy document
Target: a real maintainable Byzantine AoE2DE bot generated by the project compiler

## 1. Executive position

The compiler is now the production system for the bot, not the product we keep polishing forever. The community evidence points to a consistent pattern: mature .per AIs are persistent strategic systems built from multiple openings, economic control, enemy adaptation, military composition, selective DUC micro, map and water handling, and recovery.

Immortal is particularly important precedent because the community AI database explicitly describes it as being made with a compiler that converts C++ into a working AI script. That validates the general direction of high-level strategy source -> compiler -> native .per -> game execution. It does not justify copying Immortal's architecture or behavior.

Bright Spark and Naga show the value of breadth: multiple strategy families, map coverage, enemy-strategy adaptation, transport or water support, and long-running maintenance. Immortal emphasizes position-aware strategy, enemy adaptation and DUC military micro.

MangudAI's public development history is an unusually useful model for our refinement loop: successive revisions addressed concrete failures such as target choice, retreat behavior, destroyed infrastructure, emergency resources, DUC placement, monks and animal micro.

Therefore the project rule is:

> Encode community practice as typed Byzantine policy, compile it deterministically into native .per, run the resulting bot in DE, record actual failures, and feed those failures back into policy.

## 2. What we are building

The first target is Byzantine Stock v1. It is not a tournament bot, not an Immortal clone, not a Naga clone, not Basilisk rebuilt under a new name, and not a giant fixed build order.

Byzantine Stock v1 should provide:

- Dark -> Feudal -> Castle progression;
- several opening families;
- map-conditioned opening selection;
- economic posture control rather than static villager choreography;
- enemy-composition detection and counter packages;
- Cataphract / Varangian Guard arbitration;
- Castle conversion with TC, siege, monastery and production expansion;
- land defense and pressure;
- water economy and naval response;
- transport and landing behavior;
- selective DUC micro;
- recovery after economic, military or water failures;
- deterministic patch-pinned compilation.

The bot is a persistent policy system whose target runtime happens to be .per.

## 3. Community lessons we should deliberately copy

### Multiple strategies, not one perfect opening

Mature community AI records show broad strategy coverage and map coverage rather than one immutable build. Bright Spark and Naga explicitly cover multiple Feudal/Fast Castle families and broad map sets.

Our compiler should therefore represent:

MAP + SCOUTING + ENEMY PRESSURE + CIV FACTS -> OPENING FAMILY

not:

BYZANTINES -> one fixed build order.

### Economy as a controller

The economy should answer three questions repeatedly:

1. What strategic objective is active?
2. What resource distribution makes that objective executable?
3. What evidence releases or changes that allocation?

The existing EconomyControllerPlan and Strategic Number control plane are therefore the right implementation surface. The current percentage recipes are policy values and must be tuned from games rather than treated as engine facts.

### Enemy adaptation as a first-class loop

Immortal, Bright Spark and Naga are all documented as capable of basing strategy on enemy strategy; Immortal also uses flank/pocket position.

Byzantine policy should therefore implement:

OBSERVE -> CLASSIFY THREAT -> SELECT COUNTER PACKAGE -> CHANGE ECONOMY -> CHANGE PRODUCTION -> CHANGE POSTURE -> ACT -> WITNESS -> REASSESS

### DUC as selective high-value execution

The community database identifies DUC military micro in strong community AIs, while Bright Spark also combines DUC with transport and enemy adaptation.

DUC should be reserved for high-value work:

- tactical target selection;
- siege and monk handling;
- exposed raid targets;
- naval target selection;
- landing support when runtime semantics permit it;
- recovery/reacquisition.

Do not turn every unit into a permanent DUC project. AIRef documents finite DUC search capacity and other hard script limits.

### Water and transport as strategic systems

Naga and Bright Spark both advertise transport/water support, and community testing still reports transport imperfections even in mature AIs. citeturn311722view0turn311722view1turn688194search5

That means our water layer must be an operational loop:

WATER DETECTION -> ECONOMIC VALUE -> DOCK -> FISHING/NAVAL POSTURE -> CONTROL -> TRANSPORT -> LAND -> FORWARD OPERATION -> RECOVERY

This is particularly important because the February 2026 Naval Overhaul materially changed naval economy and combat, and the September 2026 patch changed naval balance and AI/pathfinding again.

### Recovery is part of the strategy

MangudAI's public changelog is a strong example: the AI improved through repeated fixes for destroyed mining infrastructure, target errors, retreats, emergency stone, DUC placement, monk avoidance and animal micro.

Our equivalent rule is: every major strategic capability gets a failure trigger, protected state, alternate path, resource release and reassessment condition.

## 4. How the compiler becomes the bot factory

| Community practice | Compiler representation |
| --- | --- |
| Multiple openings | OpeningSelectorPlan |
| Map behavior | MapProfile |
| Economic posture | EconomyControllerPlan + SN control |
| Persistent strategic state | Goal/SN control plane |
| Strategic triggers | typed observations |
| Counter packages | strategic demands + military compositions |
| Unit/building/tech facts | EffectiveCivData |
| Production | production demand + arbitration |
| Construction/research | lifecycle + witness + release |
| Attack behavior | AttackExecution + controller state |
| Unit micro | DUC SearchSession / TargetSession |
| Resource control | escrow/resource policy |
| Recovery | invalidation + reassessment + recovery demand |
| Patch changes | versioned GameData + provenance |
| Native safety | semantic validation + parser zero-findings |
| Regression prevention | focused behavior fixtures + deterministic CI |

The division of labor is explicit:

Policy says what the Byzantine bot should attempt.
The compiler proves whether that policy can be represented safely.
The game determines whether the policy was actually good.

### Build artifact for every promoted bot revision

Each promoted bot revision should produce one deterministic evidence package containing:

- the StrategyProfile policy fingerprint;
- the effective patch/civ fingerprint;
- the generated Byzantine .per artifact;
- the native zero-findings report;
- the compiler regression result;
- the deterministic artifact hash;
- the runtime test-matrix manifest;
- the recorded behavior/failure notes that justified the change.

That package becomes the bridge between compiler state and game state. A bot revision is promoted because the policy change is understood, the artifact is reproducible, and the runtime observation that motivated it is recorded.

## 5. Byzantine bot architecture

### A. MapProfile

Initial envelopes:

- Arabia / open land
- Arena / closed land
- standard land
- hybrid
- islands / full water

MapProfile provides default strategy families, water relevance, scouting priorities, defensive posture, economy assumptions and transport relevance. It must remain policy metadata rather than pretending to know a native fact the engine does not expose.

### B. Opening selector

Initial families:

DEFENSIVE_STANDARD
COUNTER_FEUDAL
FAST_CASTLE
WATER_ECONOMY
WATER_CONTROL
EMERGENCY_RECOVERY

Selection becomes durable after commitment. The selector should later incorporate map quality, scouting, enemy civilization signals and actual early military evidence.

### C. Economy controller

Control:

- food priority;
- wood priority;
- gold priority;
- builder share;
- emergency reserve;
- farms and dropsites;
- market/recovery behavior;
- TC expansion;
- military and water conversion.

Every allocation needs an owner, reason, release condition, arbitration identity and recovery path.

### D. Threat controller

First threat families:

- cavalry;
- ranged;
- infantry;
- siege;
- naval;
- low-pressure/boom;
- static/fortified defense.

The controller chooses a problem, not merely a unit.

### E. Byzantine premium-unit arbitration

Update 185872 gave Byzantines Varangian Guards, increased Cataphract anti-infantry damage, and changed Logistica so Cataphracts and Varangian Guards both deal trample damage.

Therefore Cataphract, Varangian Guard, Heavy Camel and Halberdier should be modeled as competing strategic responses whose value depends on enemy composition, gold, production capacity and posture.

### F. Military composition

Initial packages:

ANTI_CAVALRY
ANTI_ARCHER
ANTI_INFANTRY
SIEGE_SUPPORT
CASTLE_POWER
NAVAL_DEFENSE
WATER_CONTROL
LANDING_FORCE
IMPERIAL_CONVERSION

Composition packages may share production providers but must retain distinct strategic ownership and release semantics.

### G. Attack controller

Use:

ASSEMBLE -> STAGE -> ATTACK -> WITNESS -> RETARGET/RETREAT -> RESET

attack-now is the action, not the whole lifecycle.

### H. Water and transport

Use:

RECOGNIZE -> DOCK -> FISH/DEFEND -> CONTROL -> TRANSPORT -> ESCORT -> LAND -> BUILD FORWARD -> HOLD/RETREAT

Do not add a transport demand without also defining the landing operation and its failure path.

### I. Recovery

Examples:

destroyed mining camp -> replace dropsite
lost dock -> reassess water value
failed Castle attempt -> emergency recovery posture
lost army -> rebuild composition
dead transport -> cancel landing and recover survivors
pressure cleared -> release the counter package

## 6. Bot build sequence

### Phase 1: Byzantine Core v1

Complete the land bot:

- Dark -> Feudal -> Castle;
- open/standard land;
- standard, counter-Feudal and Fast Castle openings;
- economy controller;
- core production;
- cavalry/ranged/infantry counters;
- Cataphract/Varangian arbitration;
- Castle conversion;
- attack lifecycle;
- basic recovery.

Gate: repeated controlled games reach Castle with coherent economy and a functioning response to common Feudal threats.

### Phase 2: Map and scouting intelligence

Add:

- stronger MapProfile selection;
- scout objectives;
- enemy-civ/opening inference;
- resource-quality assessment;
- wall/forward opportunity signals;
- water valuation.

Gate: the bot should visibly make different strategic decisions on open land, closed land, hybrid and island maps rather than behaving like one build order with exceptions.

### Phase 3: Water and transport

Add:

- dock placement policy;
- fishing continuity;
- naval defense;
- naval control;
- fleet replacement;
- transport readiness;
- escort;
- landing;
- forward builder support;
- landing recovery.

Gate: island/hybrid games should produce a coherent water economy and, when appropriate, an actual landing operation.

### Phase 4: Imperial conversion

Add:

- production expansion;
- late-game upgrades;
- siege mass;
- relic conversion;
- trash economy;
- gold depletion;
- wonder/endgame behavior.

Gate: the bot must have a coherent post-Castle plan rather than continuing Castle behavior until the match collapses.

### Phase 5: strategic refinement

Add only where supported by evidence:

- richer threat severity;
- better counter ratios;
- stronger DUC targets;
- better retreat;
- rebuilding/new-base logic;
- ally assistance;
- broader team-game behavior.

## 7. The actual development loop

Every game is an experiment.

### Observe

Record at least:

- map and opening;
- age timings;
- villager count and idle TC;
- resource floats and worker distribution;
- military composition;
- production uptime;
- building losses;
- attack timing and result;
- DUC activity;
- water/transport losses;
- recovery events;
- final failure state.

### Diagnose

Every failure is classified as one of:

POLICY_WRONG
POLICY_MISSING
NATIVE_SEMANTIC_GAP
RUNTIME_UNKNOWN
GAME_DATA_GAP
COMPILER_BUG

This classification prevents the recurring mistake of modifying compiler infrastructure when the real problem is simply a bad strategy choice.

### Encode

Strategic failure -> modify StrategyProfile policy.
Representation failure -> extend typed IR/lowering.
Native uncertainty -> add a runtime probe; do not invent a compiler fact.

### Compile

Run semantic validation, control/resource validation, native parser acceptance, deterministic artifact generation, and the relevant focused behavior fixtures.

### Replay

Re-run the same scenario. The desired result is not that the new game looked nicer. The desired result is that the reproduced failure disappears.

### Promote

Only reproducible, justified behavior becomes permanent policy.

## 8. Runtime test matrix

| Dimension | Initial values |
| --- | --- |
| Map | Arabia, Arena, Islands, Hybrid |
| Opening | standard, counter-Feudal, Fast Castle, water |
| Enemy military | cavalry, archers, infantry, mixed |
| Enemy economy | pressure, standard, boom |
| Water | none, contested, dominant |
| Target phase | Feudal, Castle, Imperial |
| Failure injection | lost building, lost army, lost dock, failed attack, transport loss |

The first matrix should be small and adversarial. Expand around actual failure modes rather than generating thousands of aimless games.

## 9. What we must not do

Do not write one enormous Byzantine .per file.
Do not copy an existing community AI.
Do not optimize benchmark strength before strategic coherence.
Do not add DUC everywhere.
Do not build a universal scheduler because one strategy needs recurring behavior.
Do not convert every community idiom into compiler infrastructure.
Do not promote community convention into engine fact.
Do not treat parser success as evidence of strategic correctness.
Do not allow dead strategic demands to persist after their battlefield reason disappears.

## 10. Definition of competent Byzantine v1

Competent v1 means the generated bot can reliably:

1. execute Dark -> Feudal -> Castle on normal land maps;
2. select among several openings;
3. maintain villager and production continuity;
4. respond differently to cavalry, ranged and infantry pressure;
5. use Cataphracts and Varangians for distinct reasons;
6. expand production without persistent resource starvation;
7. attack through a persistent controller;
8. recover from common economic and military losses;
9. use water when water matters;
10. execute a basic transport/landing operation where appropriate;
11. reassess after battlefield conditions change;
12. compile deterministically and pass native zero-findings acceptance.

Runtime competence remains a game result, never a compiler claim.

## 11. Definition of mature Byzantine bot

A later mature version should additionally handle:

- broader map families;
- walled and fortified opponents;
- adaptive enemy strategy rather than simple unit-count response;
- selective high-value DUC;
- reliable naval control and transport invasion;
- rebuilt/forward bases;
- relics, trade, gold depletion, trash transitions and endgame;
- patch evolution without strategic regression;
- meaningful team-game roles.

Community evidence indicates that breadth, adaptation, DUC and map coverage are individually expensive. That is why the project should develop them in stages rather than pretending everything can close simultaneously.

## 12. Immediate implementation sequence

1. Build Byzantine Core v1 on the already-closed compiler substrate.
2. Turn MapProfile and opening selection into meaningful scouting-conditioned behavior.
3. Expand the counter matrix and production arbitration.
4. Tune Cataphract/Varangian arbitration from real games.
5. Connect the water execution substrate to strategic water demand.
6. Add only the highest-value DUC behaviors.
7. Turn observed failures into recovery contracts.
8. Add Imperial conversion.
9. Iterate through an adversarial game matrix.

At this point the highest-value work is bot construction and playtesting, not another generic compiler subsystem.

## 13. Project rule

> A compiler feature is justified by a bot behavior that needs it. A bot feature is justified by strategy evidence or a reproducible game failure.

That rule is the bridge between the community corpus and this compiler.
