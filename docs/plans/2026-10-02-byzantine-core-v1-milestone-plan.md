
# Byzantine Core v1 Milestone Plan

> For agentic workers: Use the host's available task-by-task implementation workflow. Steps use checkbox syntax for tracking.

**Goal:** Turn the verified Byzantine compiler strategy into a real first-version land bot with multiple openings, economic control, Feudal counterplay, Castle conversion, Byzantine premium-unit arbitration, attack/recovery behavior, and a repeatable DE acceptance matrix.

**Architecture:** Core v1 reuses the existing typed strategy, persistent-control, production, military-composition, DUC, attack, and recovery seams. The work is primarily strategy synthesis and integration, not another generic compiler subsystem. Each milestone must produce both a static compiler artifact and a behaviorally testable bot revision.

**Tech Stack:** Python 3.12 for compiler/test execution, repository-native typed IR and native lowering, pinned aoe2-ai-parser, AoE2DE for live behavioral acceptance, GitHub Actions for compiler CI.

## Global Constraints

- main remains the compiler source of truth.
- The canonical strategy entry point is build_byzantine_strategy(effective).
- Current patch binding is ByzantineProfile.for_update_185872().
- Reuse existing typed seams. Do not introduce a universal scheduler or a second .per language.
- Preserve OBSERVATION -> ARBITRATION -> EXECUTION -> WITNESS -> RECOVERY -> REASSESSMENT.
- can-* is admission only; action issuance is not a witness; pending is not completion; timers are cadence, not strategic truth.
- Runtime-unknown native behavior stays OPEN/UNKNOWN until directly probed.
- A strategy failure is not automatically a compiler failure.
- Existing native acceptance is static compiler evidence, not live-DE evidence.
- The repository currently has no verified automated DE game runner. The DE tests below are manual/externally executed acceptance cases until a live-DE harness is deliberately added.
- Proposed bot build artifact path: dist/byzantine/Byzantine.per. Installing directly into the Steam AoE2DE AI directory is a deployment operation and is not part of compiler compilation.
- A milestone is complete only when its focused compiler tests, native acceptance, and specified DE cases have all passed and the evidence is recorded.

## Core v1 completion contract

Core v1 is not a claim that the bot is strong.

It is a claim that the bot is a functioning Byzantine player with a coherent control loop:

MAP/OBSERVATION -> OPENING -> ECONOMY -> THREAT -> COUNTER -> CASTLE CONVERSION -> MILITARY ACTION -> WITNESS -> RECOVERY -> REASSESSMENT

The v1 bot must demonstrate this loop in actual DE play on the acceptance matrix.

A compiler pass is not a live-game pass.

A parser pass is not a strategy pass.

A single successful game is not a behavioral regression test.

The useful milestone boundary is reached only when the generated Byzantine artifact survives both the compiler and the game.

## Explicit non-goals for Core v1

Core v1 does not require:
- Imperial completeness;
- relic strategy;
- trade strategy;
- full water/transport execution;
- late-game trash optimization;
- team-game specialization;
- broad DUC tactical micro;
- every community opening.

Those belong to later milestones and should be added only when a reproducible behavior or documented community pattern justifies them.

## Execution order

Implement in this order:

1. Milestone 0: reproducible bot artifact.
2. Milestone 1: opening + early economy behavior.
3. Milestone 2: Feudal counters.
4. Milestone 3: Castle conversion + premium units.
5. Milestone 4: attack + recovery.
6. Milestone 5: integrated DE acceptance matrix.

Do not advance a milestone by weakening its acceptance criteria. Humans already invented “technically passes” as a substitute for reality. The bot project does not need another one.
