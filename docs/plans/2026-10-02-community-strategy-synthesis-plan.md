# Implementation Plan: Community Strategy Synthesis

## Objective

Turn the remaining strategy gap into an executable Byzantine stock-style strategy surface without reopening accepted generic compiler substrate.

## Work packages

### WP1 — Strategy contract and evidence ledger
- add the strategic behavioral contract;
- add source/provenance records for each synthesized pack;
- preserve ENGINE / COMMUNITY / POLICY / OPEN boundaries.

### WP2 — Economic and research synthesis
- add Imperial trajectory;
- add Castle economic expansion;
- add a bounded research pack;
- use existing escrow/resource-protection surfaces;
- add deterministic recovery and invalidation tests.

### WP3 — Production and composition synthesis
- add provider-capability demands for common Castle production;
- add composition floors;
- extend composition proof assembly;
- preserve current counter-package arbitration.

### WP4 — Information, fortification, siege, Monk strategy
- add explicit observations for enemy composition, structures, exposure and strategic opportunity where native facts are proven;
- add safe capability demands;
- keep location-sensitive placement and relic acquisition OPEN.

### WP5 — Persistent control and recovery
- extend current SN modes only where catalog semantics are documented;
- add recovery/reassertion policy to the strategy profile;
- ensure temporary capability loss never invalidates strategic intent.

### WP6 — Community corpus registry
- register the higher-value recurring community idioms;
- connect each idiom to a semantic owner;
- mark remaining runtime questions rather than inventing facts.

### WP7 — Acceptance
- focused strategy tests;
- native zero-findings fixture;
- full compiler test suite;
- determinism/snapshot verification;
- audit main after integration.

## Implementation order

1. Contract + evidence registry.
2. Economic/research profile.
3. Production/composition profile.
4. Fortification/siege/Monk profile.
5. Recovery/control integration.
6. Corpus registry.
7. Focused tests.
8. PR CI.
9. Merge only on green candidate.
10. Audit main and update PROJECT_STATE.

## Exit criteria

The branch is acceptable only when:
- all new profile facts resolve against current EffectiveCivData;
- no existing closed DUC/attack seam is reopened;
- unknown runtime behavior remains explicitly OPEN;
- generated native .per passes zero-findings;
- full compiler tests pass;
- deterministic outputs are unchanged for existing profiles;
- new profile fingerprints are deterministic;
- main contains the merged strategy synthesis and refreshed state documentation.
